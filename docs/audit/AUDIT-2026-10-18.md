What holds up well: postings happen in one transaction with the business record, audit and outbox. Idempotency keys are unique, and a replay with a different body is refused (`IDEMPOTENCY_CONFLICT`). ## H1 — A committed journal batch can be made unbalanced · high

**Where:** `functions/src/db/migrations/001_core.ts:173-196`
**What's wrong:** `assert_batch_balanced` is a deferred constraint trigger on **`journal_batches` insert** only. It checks the batch once, at the commit of the transaction that created it. Later inserts into `journal_lines` for that batch are never checked. The append-only triggers block `UPDATE` and `DELETE`, not `INSERT`. So "every batch balances" is enforced by the posting code, not by the database as the migration header and BUILD_PLAN §3 say.
**Failing scenario (reproduced):** a balanced batch is committed (2000 debit / 2000 credit). A second transaction runs
`insert into journal_lines (batch_id, account_id, side, amount_pesewas) values (<that batch>, <member account>, 'CREDIT', 99900);`
It succeeds. The batch now shows debits 2000 and credits 101900, and no error is raised. A bug in any future posting path (or a manual fix by an operator) could do the same.
**Suggested fix:** add `create constraint trigger journal_lines_balanced after insert on journal_lines deferrable initially deferred for each row execute function assert_lines_batch_balanced()`, which re-checks `new.batch_id`. Also refuse lines for a batch that was not inserted in the current transaction, for example by comparing the batch row's `xmin` with `pg_current_xact_id()`. Add a test that appends a line to a committed batch and expects `P0001`.

## H2 — Device binding is a claim the phone makes, not something it proves · high

**Where:** `functions/src/commands/processAgentCommand.ts:62-78`, `firestore.rules:44-55`, API.md §3
**What's wrong:** `deviceId` is a string the client chooses. It is shown on screen so a supervisor can bind it, and it is sent in clear in every command. The server checks only that the string is bound to the signed-in agent. Nothing ties the command to the physical company phone: no hardware key, no signature, and Firestore App Check enforcement is a console setting that isn't recorded anywhere in the repo.
**Failing scenario:** an agent's password is phished, or the agent colludes. From any device or a script, the attacker signs in as the agent and writes `commands/{uuid}` with the agent's known `deviceId`. Each fake `COLLECTION` credits a member's Susu balance. With a colluding member, that balance later becomes a withdrawal request for money that was never collected. The custody shortfall surfaces at handover, but only after the fact, and it lands on the agent pair.
**Suggested fix (needs a contract change):** at install time, generate a non-exportable Android Keystore key (with key attestation). `bindDevice` stores the public key. Each command carries `sig` = signature over `commandId|seq|capturedAt|canonical(payload)`, and the trigger verifies it. Rules would add `sig` to `hasOnly`. Until then: enforce App Check on Firestore with the Play Integrity "device recognised + app recognised" verdict, and record the enforcement in a deploy checklist. Add a rules or unit test proving that a command whose signature doesn't verify is `REJECTED`.

## M1 — Callables trust token claims alone, so a demoted or removed person keeps power for up to an hour · medium

**Where:** `functions/src/callables/staffCallable.ts:32-44`
**What's wrong:** the role comes only from the ID token. `staff_users.status` and `staff_users.role` are never read, tokens are not checked for revocation, and nothing calls `revokeRefreshTokens` when claims change.
**Failing scenario:** a branch manager is removed after a cash irregularity. For up to 60 minutes their existing token still passes `requireRole(['SUPER_ADMIN','BRANCH_MANAGER'])`. In that window they can create agents, pair them and bind devices. Once Step 6 lands, the same gap applies to approvals.
**Suggested fix:** in `staffCallable`, load the `staff_users` row inside the request and require `status = 'ACTIVE'` and `role = claims.role` (and the same branch set). On any role change or disable, call `getAuth().revokeRefreshTokens(uid)`. For money-out callables, use `verifyIdToken(token, true)`-equivalent revocation checking.

## M2 — `createStaffUser` acts before it authorises, and leaks whether an email exists · medium

**Where:** `functions/src/callables/index.ts:29-42`; permission checks live in `functions/src/org/staff.ts:18-26`
**What's wrong:** the Firebase Auth user is created before `requireRole` runs, and deleted again if the database step fails. `auth/email-already-exists` is not a `DomainError`, so it surfaces as `internal`.
**Failing scenario (reproduced on the emulator):** a user with role `CASHIER` calls `createStaffUser` for a new email and gets `permission-denied NOT_PERMITTED`. For an existing email (`admin@susu.test`) they get `internal`. Any signed-in staff member can therefore test whether an email belongs to a staff account. Each refused call also briefly creates a real Auth user. An admin adding a duplicate email sees "Something went wrong" instead of "already exists".
**Suggested fix:** run the role and branch checks (a pure function over `actor` and `input`) before `auth.createUser`. After authorisation, map `auth/email-already-exists` to `DomainError('CONFLICT')`. Add both cases to the tests.

## M3 — Two concurrent `createAgentPair` calls can put one agent in two active pairs · medium

**Where:** `functions/src/org/agentPairs.ts:32-37`, `functions/src/callables/index.ts:45-53`
**What's wrong:** "one active pair per agent" is a `select … where status = 'ACTIVE'` with no lock and no constraint. The claims update afterwards is last-writer-wins.
**Failing scenario:** two managers (or a double-click on a slow network) pair agent X with Y and with Z at the same moment. Both transactions pass the `busy` check and commit. X is now in two pairs with two custody accounts, but X's token carries only one `agentPairId`. X's device is bound to one pair while their route comes from the other, and collections credit the wrong pair's custody.
**Suggested fix:** inside the transaction, `select … from staff_users where uid = any($1) for update` before the busy check. Better still, add an `agent_pair_members (agent_uid text primary key, agent_pair_id uuid)` table, or a unique partial index per agent column, so the database refuses the second pair.

## M4 — Balance projections can be rewritten, or driven negative, with no database guard · medium

**Where:** `functions/src/db/migrations/001_core.ts:124-129`
**What's wrong:** `account_balances` has no trigger and no check. "Never below zero" for non-negative accounts lives only in `postJournal`. Nothing reconciles balances against `journal_lines`.
**Failing scenario (reproduced):** `update account_balances set balance_pesewas = 5000000 where account_id = <member>` succeeds, and so does `= -1` on a custody account with `allow_negative = false`. A member's displayed balance (and future withdrawal checks) now disagrees with the journal, and nothing notices.
**Suggested fix:** add a trigger that rejects a negative balance when the account's `allow_negative` is false, and rejects any update whose delta is not matched by lines in the same transaction (or only allow updates from the posting function's role). Add a scheduled reconciliation job, plus a test, asserting `balance = Σ signed lines` for every account.

## M5 — The maker-checker `CHECK` on members can be sidestepped by editing the maker · medium

**Where:** `functions/src/db/migrations/001_core.ts:71-89`, `functions/src/members/members.ts:57-86`
**What's wrong:** `check (approved_by is null or approved_by <> created_by)` compares two mutable columns of the same row. `members` has no append-only or immutable-column protection.
**Failing scenario (reproduced):** `update members set created_by = 'someone-else'`, then `update members set status = 'ACTIVE', approved_by = '<original maker>'`. Both succeed, and the maker has approved their own registration. Today this needs direct database access. It's the same shape that every future request/approval table will copy.
**Suggested fix:** add a trigger that forbids changes to `created_by`, `ghana_card_number`, `consent_at` and `branch_id` after insert, and that only allows `status` to change from `PENDING_APPROVAL` when `approved_by` is set in the same update. Put future approvals (Step 6) in their own append-only `approvals` table, with a `CHECK` comparing to the immutable request row. Also, before `reverseJournalBatch` is exposed, make sure `approvedBy` comes from a recorded approval and never from caller input (`functions/src/ledger/reverse.ts:6-13`).

## M6 — `registerMember.photoPaths` accepts any path, which opens a cross-member KYC read once `getMember` signs URLs · medium

**Where:** `packages/shared/src/requests.ts:76` (`z.array(z.string().max(512))`), `functions/src/members/members.ts:36-39`, API.md §5
**What's wrong:** paths are stored verbatim. Nothing checks that they are under `kyc-inbox/{caller uid}/`, that they exist, or that they belong to this registration.
**Failing scenario:** once `getMember` (planned) returns short-lived signed URLs for `photo_paths`, any staff member who can register a member can pass another member's locked `kyc/…` path, or another user's inbox path, in `photoPaths`. Opening their own new member then signs a URL to someone else's Ghana Card image.
**Suggested fix:** validate each path against `^kyc-inbox/${actor.uid}/[0-9a-f-]{36}\.(jpg|png|webp)$`, check the object exists, and move it into `kyc/{memberId}/` in the same flow. Only ever sign URLs for paths under `kyc/{memberId}/`.

## M7 — Collections can still post for agents who are no longer in that pair · medium

**Where:** `functions/src/commands/processAgentCommand.ts:62-78`, `functions/src/org/devices.ts:80-91`
**What's wrong:** authorisation checks `devices.status` and `devices.agent_uid` only. It does not check `staff_users.status`, `agent_pairs.status`, or that the agent is still `agent_a_uid`/`agent_b_uid` of `devices.agent_pair_id`.
**Failing scenario:** an agent moves to a new pair (or the old pair is deactivated once that API exists) and nobody revokes the phone. Collections keep posting into the **old** pair's custody account. The new partner's handover won't match, and the old pair's custody grows with cash it never held.
**Suggested fix:** in `getDevice`, join `staff_users` and `agent_pairs`. Reject with `DEVICE_REVOKED`/`NOT_PERMITTED` when the agent is not `ACTIVE`, the pair is not `ACTIVE`, or the agent is not one of the pair's two members. Add tests for each case.

## M8 — `FAILED` promises a notification that does not exist, and failed collections are never retried · medium

**Where:** `functions/src/triggers/agentCommands.ts:26-36`
**What's wrong:** after 6 hours of infrastructure errors the document is marked `FAILED` with "Your supervisor has been notified." No notification, case, dashboard counter or outbox row is written. After `FAILED`, nothing tries the command again. The agent cannot resubmit the same UUID (rules forbid updates), and the API forbids reusing it.
**Failing scenario:** Cloud SQL is down for an afternoon. Twenty collections go `FAILED`. The cash is in the agents' bags, members got no receipt, and the branch sees nothing, because no queue lists these. If agents re-enter them with new UUIDs, the originals become a reconciliation trap if anyone ever reprocesses them.
**Suggested fix:** when marking `FAILED`, also write an exception record (Firestore `exceptions/` or a Postgres `cases` row via a retryable path) and bump `pendingSyncCount`/`exceptions` on the dashboard. Add a scheduled sweeper that reprocesses `FAILED` commands (safe, because processing is idempotent per command ID), and tell agents in the app not to re-enter them.

## L1 — Out-of-order and missing `seq` numbers are not handled · low

**Where:** `functions/src/commands/processAgentCommand.ts:70-76`; BUILD_PLAN §5 ("the server holds out-of-order ones as pending")
**What's wrong:** `seq` is only checked for reuse. Gaps (an app crash between reserving a number and writing) and reordering are neither held nor reported. A deleted app or a wiped cache shows up as a permanent gap nobody sees.
**Suggested fix:** record `max(seq)` per device. Surface gaps on the supervisor's sync-health view instead of blocking, because the agent app reserves a number before writing, so a crash can legitimately leave a gap. Update BUILD_PLAN §5 to match whatever is chosen.

## L2 — Racing duplicates go through an "infrastructure error and retry" path · low

**Where:** `functions/src/commands/processAgentCommand.ts:37-59`, `:95-100`
**What's wrong:** two concurrent deliveries of one command both pass `loadPreviousResult`. The second replays the posting, then hits a primary-key violation on `collections` (`23505`), which is not a `DomainError`, so the trigger throws and retries. The same applies to two commands with the same `(device_id, seq)`. The money stays correct (the transaction rolls back), but every race costs a retry and an error log, and `on conflict (id)` in `recordCommand` misses the `(device_id, seq)` constraint.
**Suggested fix:** take `pg_advisory_xact_lock(hashtext(commandId))` at the start of the transaction, or treat `23505` on these two constraints as "load the previous result".

## L3 — The database does not check that a reversal mirrors its original · low

**Where:** `functions/src/db/migrations/001_core.ts:156-160`
**What's wrong:** a batch with `reverses_batch_id` can carry any balanced lines (reproduced: a 1-pesewa "reversal" of a 2000-pesewa batch was accepted). Only `reverseJournalBatch` keeps it honest. Because the unique index allows one reversal per batch, a wrong one blocks the correct one.
**Suggested fix:** at commit, a constraint trigger compares the reversal's lines with the original's, with sides swapped.

## L4 — A duplicate Ghana Card error returns the other member's ID across branches · low

**Where:** `functions/src/members/members.ts:27-34`
**Failing scenario:** an agent in branch A registers a card that belongs to a member in branch B. `details.memberId` returns B's member ID, which is enough to probe other branches with future `getMember` calls (these should still be refused by scoping).
**Suggested fix:** return `memberId` only when `canAccessBranch(actor, existing.branch_id)`. Otherwise just say "already registered, contact the branch".

## L5 — Local setup can hit production, and the secrets file isn't ignored · low

It also prompts for `FUNCTIONS_REGION` and writes the answer to `functions/.env.local`. `functions/.secret.local`, which API.md §6 tells developers to create, is **not** in `.gitignore`.

Document `--project demo-susu` for local runs, and add a `migrate` script for the local database. Note: this audit's emulator run created `functions/.env.local` (`FUNCTIONS_REGION=europe-west1`, git-ignored) when the default region prompt was accepted. Keep or delete it as you prefer.

## Proposed tests for the backend

1. Append a `journal_lines` row to a committed batch → expect `P0001` (H1).
2. `update account_balances` with a negative value on a non-negative account → expect an error (M4).
3. Change `members.created_by` → expect an error (M5).
4. `createStaffUser` as CASHIER for an existing email → expect `permission-denied`, and no Auth user is created (M2).
5. Two concurrent `createAgentPair` calls sharing one agent → exactly one succeeds (M3).
6. A command from a device whose agent is `DISABLED`, whose pair is `INACTIVE`, or who has left the pair → `REJECTED` (M7).
7. `registerMember` with a `photoPaths` entry outside `kyc-inbox/{uid}/` → `invalid-argument` (M6).
8. A command still failing after 6 h → `FAILED` plus an exception record (M8).
